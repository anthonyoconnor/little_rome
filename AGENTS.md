# Little Rome

Follow [the development rules](development-rules.md) for milestones, Git checkpoints, fast automated validation, and progress screenshots. These workflow rules take precedence over conflicting process guidance in design documents or project skills. No human testing will be carried out.

Read [the overview](little-rome-overview.md) and [the gameplay rules](little-rome-gameplay.md) before changing the game. They define the current build-and-watch design; older monthly-turn designs do not apply.

## Skills

Use [little-rome-dream-loop](.agents/skills/little-rome-dream-loop/SKILL.md) for the local build, capture, critique, and refine workflow. Its two references cover iteration and Blender assets.

## Scope and evidence

- Respect the active request. Preparation-only work may change skills, references, and tooling checks, but must not begin the game, produce its asset library, or start an implementation loop. A later explicit request to build or continue the game authorizes that work without another confirmation.
- The two design documents govern mechanics. The six images in concept_art govern visual quality; image labels and scenery do not add gameplay systems.
- Use Blender for the game's authored 3D assets. Keep editable sources and verify their exported appearance in the browser.
- Keep simulation state independent of rendering and playback speed. Resource movement, task animation, shortages, and rewind must agree.
- Judge the actual running browser build against the original art. An offline render or generated image is reference material, not evidence that the game works.
- Keep proposed tuning separate from confirmed rules. Do not describe unrun tests or subjective scores as completed gameplay validation.
- Preserve source art and existing user changes. Local preparation does not authorize publishing, external paid services, or unrelated configuration changes.
